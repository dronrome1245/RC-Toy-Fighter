# Правила ведения проекта

## 1. Обязательный вход для любой нейросети

Проект ведётся из разных чатов и разными нейросетями.

Перед работой читать:

1. `00_AI_START_HERE.md`;
2. `STATUS.md`;
3. `00_РУКОВОДСТВО_ДЛЯ_ВЗРОСЛОГО.md`;
4. `DECISIONS.md`;
5. `HISTORY.md`;
6. `SOURCES.md`;
7. этот файл;
8. профильные файлы задачи.

Если контекст не прочитан, нельзя угадывать текущее состояние.

## 2. Репозиторий предназначен для взрослого

Основная документация должна быть:

- технически точной;
- компактной;
- структурированной;
- пригодной для практической работы;
- без обязательного упрощения до уровня ребёнка.

Ребёнок не обязан читать репозиторий.

Детский слой — вспомогательный: картинки, схемы, короткие задания, карточки этапов и совместные эксперименты.

## 3. Единственный источник текущего состояния

`STATUS.md` — единственный файл, где хранится:

- текущий этап;
- завершённые действия;
- блокирующие вопросы;
- следующий практический шаг;
- что сейчас разрешено/запрещено покупать или делать.

Не создавать параллельные файлы статуса.

## 4. История решений

`DECISIONS.md` — append-only журнал.

Если решение изменилось:

1. старое пометить `ЗАМЕНЕНО`;
2. указать новое решение;
3. объяснить причину изменения;
4. не удалять старую запись.

## 5. История действий

`HISTORY.md` — append-only хронология фактически выполненного.

Не переписывать историю задним числом.

## 6. Источники

`SOURCES.md` хранит:

- исходное видео;
- карточки товаров;
- паспорта и характеристики;
- внешние примеры;
- фактические измерения нашего самолёта.

Факт, предположение и пользовательское решение должны различаться.

## 7. Обязательная синхронизация

После существенной работы до завершения ответа проверить необходимость обновления:

- `STATUS.md`;
- `DECISIONS.md`;
- `HISTORY.md`;
- `SOURCES.md`.

Нельзя заявлять, что решение «зафиксировано», если оно не записано при доступной записи в GitHub.

## 8. Иерархия истины

1. последнее явное решение пользователя;
2. `STATUS.md`;
3. более поздняя запись `DECISIONS.md`;
4. актуальный профильный документ;
5. старые материалы.

## 9. Требование к техническим решениям

Каждое существенное решение должно содержать:

- выбранный вариант;
- причину;
- расчёт/характеристики/источник;
- ограничения;
- что ещё проверить физически;
- влияние на следующий этап.

Для покупной электроники обязательно проверять:

- массу;
- размеры;
- напряжение;
- ток;
- совместимость разъёмов;
- схему питания;
- число каналов;
- физическое размещение;
- влияние на центр тяжести.

## 10. Базовый донор

Проект строится под уже заказанный пенопластовый самолёт-запускалку 35 см, Ozon product id `5530158944`.

Конфигурация для условного 68-см планера (`2204 / ESC 20A / 2S / 5030 / 5–9г сервы`) отменена.

До фактических измерений 35-см самолёта конкретная силовая электроника не утверждается.

## 11. Работа с ребёнком

Педагогическая цель сохраняется: ребёнок должен участвовать и видеть полный цикл проекта.

Но это организует взрослый, а не документация.

На каждом крупном практическом этапе желательно дать ребёнку одно безопасное действие:

- взвесить;
- измерить вместе со взрослым;
- посчитать;
- выбрать;
- сделать прогноз;
- сравнить результат с ожиданием;
- поставить отметку о завершении;
- сделать фотографию результата.

Не требуется создавать детскую копию каждого технического документа.

## 12. Визуальные материалы

Схемы и фотографии используются там, где они ускоряют понимание монтажа, расположения деталей или результата испытания.

`08_Картинки_для_понимания/` — вспомогательный визуальный раздел, а не основной маршрут репозитория.

После получения самолёта предпочтение отдаётся фотографиям нашего фактического экземпляра.

## 13. Безопасность

Только взрослому:

- нож и резка;
- сверление;
- пайка;
- зарядка/обслуживание LiPo;
- первый запуск двигателя;
- работа рядом с вращающимся винтом;
- переделка силовой схемы.

Ребёнок не держит модель при работающем винте.

## 14. Завершение проекта

Проект закрывается только когда:

- модель имеет финальный технический статус;
- выполнены наземные проверки;
- проведён полёт либо зафиксирована объективная причина невозможности полёта;
- результат испытаний записан;
- все открытые задачи имеют итоговый статус;
- зафиксировано, чему научились и что пришлось исправлять.

Первый успешный полёт сам по себе не означает завершение проекта.
